# Источники тестовых векторов

`OfficialHashVectors.h` содержит 287 примеров с заранее опубликованными результатами:

- SHA-512/224 и SHA-512/256: все 129 примеров `ShortMsg` и первые/последние два примера `LongMsg` для каждого алгоритма из [NIST CAVP SHS](https://csrc.nist.gov/CSRC/media/Projects/Cryptographic-Algorithm-Validation-Program/documents/shs/shabytetestvectors.zip).
- SHAKE128-256 и SHAKE256-512: все 9 и 5 примеров `VariableOut` с выходом соответственно 256 и 512 бит из [NIST CAVP SHAKE](https://csrc.nist.gov/CSRC/media/Projects/Cryptographic-Algorithm-Validation-Program/documents/sha3/shakebytetestvectors.zip). SHAKE позволяет брать префиксы выхода, но здесь сравнивается весь запрошенный результат.
- Стрибог-256 и Стрибог-512: оба сообщения из раздела 10 [RFC 6986](https://www.rfc-editor.org/rfc/rfc6986.html). Порядок байтов полных сообщений и результатов развёрнут относительно записи битовых векторов в RFC; биты внутри байта не переставляются. RFC имеет информационный статус.
- `belt-hash`: три примера [спецификации СТБ 34.101.31](https://github.com/bcrypto/belt/blob/master/spec/9111TestHash.tex), длины сообщений 13, 32 и 48 байтов. Описание алгоритма: [раздел «Хэширование»](https://github.com/bcrypto/belt/blob/master/spec/0708Hash.tex).

SHA-256 загруженных архивов NIST:

```text
929ef80b7b3418aca026643f6f248815913b60e01741a44bba9e118067f4c9b8  shabytetestvectors.zip
debfebc3157b3ceea002b84ca38476420389a3bf7e97dc5f53ea4689a16de4c7  shakebytetestvectors.zip
```

Каждый официальный пример проверяется через производственный адаптер алгоритма при размерах порции 1, 31, 127 и 8192 байта. Проверяется размер результата и защитная область после выходного буфера.

`AdditionalHashVectors.h` дополняет официальные примеры 72 результатами независимой реализации Python `hashlib`/OpenSSL: четыре новых алгоритма SHA-512/t и SHAKE, 18 размеров от пустого сообщения до 2 МиБ + 17 байтов, включая границы блоков и дополнения. Генератор `GenerateHashVectors.py --check` проверяет неизменность этих значений в CI. Данные воспроизводимы: байт с индексом `i` равен `(i * 71 + 19) & 255`.

Начальные значения SHA-512/t сверены с §5.3.6 [FIPS 180-4](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.180-4.pdf). Параметры SHAKE и разделение доменов сверены с §6.2 [FIPS 202](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.202.pdf). SHA-512/t не является обычным усечённым SHA-512; SHAKE не является усечённым SHA3.

Прохождение этих тестов не означает сертификацию FIPS/CAVP или сертификацию по национальным стандартам.

Дополнительные известные ответы в `CoreTests.cpp` покрывают остальные зарегистрированные алгоритмы. Тест требует наличия хотя бы одного заранее заданного ответа для каждого из 36 названий:

- XXH32/64 и XXH3-64/128: пустое сообщение и нулевой seed из `cli/xsum_sanity_check.c` закреплённого подмодуля [xxHash](https://github.com/Cyan4973/xxHash).
- BLAKE3-256/512: префиксы официального `test_vectors/test_vectors.json` закреплённого подмодуля [BLAKE3](https://github.com/BLAKE3-team/BLAKE3).
- BLAKE2sp: пустое сообщение без ключа из [векторов авторов BLAKE2](https://github.com/BLAKE2/BLAKE2/blob/master/testvectors/blake2-kat.json), SHA-256 загруженного JSON `5031ac14800798ae15cee79c04d65e326a575f2c968c7e2846a79bd07a1c0e61`.
- SHA3-224/384/512 и KangarooTwelve: файлы `tests/TestVectors/ShortMsgKAT_SHA3-*.txt` и `KangarooTwelve.txt` закреплённого [XKCP](https://github.com/XKCP/XKCP). Для K12-264 проверяется 33-байтный префикс опубликованного 64-байтного ответа; размер результата не меняет префикс XOF.
- CRC64/XZ: `123456789`, проверено независимой `lzma_crc64` из XZ Utils; [формат XZ](https://tukaani.org/xz/format.html). RIPEMD-160: `abc`, проверено OpenSSL/hashlib и соответствует [примерам авторов](https://homes.esat.kuleuven.be/~bosselae/ripemd160.html).
- eD2k обоих вариантов: `abc` совпадает с MD4 сообщения короче блока; дополнительно проверяются границы блоков и составной результат. QuickXorHash пустого сообщения — 20 нулевых байтов по [описанию Microsoft](https://learn.microsoft.com/en-us/onedrive/developer/code-snippets/quickxorhash).

`StreamingHashVectors.h` содержит ещё 123 опубликованных примера: все 35 длин BLAKE3 из авторского JSON для вывода 256 и 512 бит; 12 длин BLAKE2sp из указанного JSON; все 35 случаев xxHash с нулевым seed из перечисленных таблиц; шесть примеров K12-256 длиной `17^0` … `17^5` из XKCP. Каждый проверяется порциями 1, 127 и 8192 байта — 369 сравнений, включая переходы дерева BLAKE3 и K12. Шаблон 0 означает байт `i % 251`, шаблон 1 — `i % 256`; шаблон 2 повторяет `XSUM_fillTestBuffer`: начальное 64-битное значение `2654435761`, байт `value >> 56`, затем умножение на `11400714785074694797` по модулю `2^64`. Это генерация входных данных, ожидаемые хеши взяты из опубликованных таблиц.

Проверка одного вызова `Update` на 512 МиБ + 17 нулевых байтах выявляет переполнение перевода байтов в биты на x86. Ожидаемый SHAKE128-256 получен через Python `hashlib.shake_128`. Для PH128-264 и PH256-528 независимо составлено сообщение cSHAKE по SP 800-185: `left_encode(8192) || Z_1 || ... || Z_65537 || right_encode(65537) || right_encode(L)`, где первые 65536 блоков содержат 8192 нулевых байта, последний — 17. `Z_i` получены через SHAKE128/256 (`hashlib`), вывод 32/64 байта соответственно; внешняя cSHAKE128/256 — через PyCryptodome с именем функции `ParallelHash` и пустой строкой настройки. Эти значения являются независимыми регрессионными примерами, а не опубликованными NIST векторами. Тест выполняется на x86, x64 и ARM64 и требует около 512 МиБ памяти.

ParallelHash также проверяется на том же сообщении порциями по 1 МиБ: общий счётчик длины должен сохраняться независимо от размера отдельного вызова. Закреплённый XKCP использует `size_t` для этого счётчика; `Algorithms/XKCP/PatchSP800185.cmake` создаёт в каталоге сборки копию с 64-битным счётчиком, числом блоков и аргументом `right_encode`. SHA-256 трёх исходных файлов проверяется до применения исправления, сам подмодуль не изменяется. Для невыровненных входных буферов включена штатная опция XKCP `NO_MISALIGNED_ACCESSES`.

Файловый путь проверяется отдельно: разреженный файл содержит 4 ГиБ нулей и 18 ASCII-байтов `OpenHashTab offset` в конце. Производственный асинхронный `ReadFile` должен прочитать и эту последнюю часть, используя `OVERLAPPED.OffsetHigh`. Эталон SHA-256 `d1885540b2b008f0bb739130d1712a275c034811aa2828648f4bd931a371d6e3` получен независимым Python `hashlib`: 4096 вызовов `update(bytes(1024*1024))`, затем `update(b'OpenHashTab offset')`. Разреженность экономит место на диске, но программа действительно читает и хеширует все 4 ГиБ + 18 байтов.

CRC64/XZ дополнительно сравнивается с независимым побитовым эталоном по §6 [формата XZ](https://tukaani.org/xz/xz-file-format.txt): все восемь смещений входного указателя, длины 0…257, начальные значения 0 и `0x123456789abcdef0`, один вызов и порции 1/7/8/31 байт — 20640 сравнений. Точный размер выделения позволяет ASan заметить чтение за концом. Пустой вход проверяется также с `nullptr`.

Для регрессии 32-битного счётчика CRC64 на 64-битной платформе Linux передаёт одним вызовом 4 ГиБ + 17 нулевых байтов из анонимного отображения памяти; ожидается `9247c1bf2ab39629`. Windows x64/ARM64 передаёт в реальный адаптер CRC64 одним вызовом отображённый разреженный файл выше, включая ненулевой хвост; ожидается `7e3fbec98de8c6b6`. Эти значения независимо получены через `lzma_crc64` из XZ Utils: начать с 0, обработать 4096 блоков из 1048576 нулевых байтов, затем 17 нулей либо ASCII `OpenHashTab offset`. Это регрессионные эталоны, не опубликованные стандартом векторы. На x86 один такой буфер не представим, но короткие и потоковые случаи выполняются полностью.
